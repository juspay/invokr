the problem

Anatomy of a hand-rolled tracker

Independently, we all converge on the same five pieces — and the same five bugs.

what everyone builds

  • A tasks table with a status column
  • A poller on a few-second tick
  • A retry_count column, incremented by hand
  • A cron entry, on one box
  • A Slack webhook for when it silently stops

what ships with it

  • Double-fire the day a second pod starts polling
  • Timers lost on deploy — they were in process memory
  • "Did it actually go out?" is unanswerable; no attempt history
  • Retry storms — fixed delay, no jitter, no ceiling
  • Credentials in config, and config is in git
We have written these too. That is where the requirements came from.
the problem

What the duplication actually costs

No invented rupee figure on this slide — you would discount it, and the argument does not need it.

  • N on-call surfaces for one class of problem
  • N places to debug one missed timer, each with different logs and vocabulary
  • No shared observability — no common metric, no common dashboard, no cross-team comparison
  • Every new team pays the tax again, from scratch, in their first quarter
  • And the failure mode is silence. A tracker that stops looks exactly like a tracker with nothing to do

what invokr is

Architecture

There is no scheduler process. The database is the scheduler.
pg_cron materializes CRON ticks inside PostgreSQL. Delayed jobs are claimed straight off the worker's pickup query when run_at <= now(). Two processes, one database, nothing holding a timer in memory.
what invokr is

Guarantees, and what makes them true

ClaimMechanism
DurableJob + execution committed to PostgreSQL before the API answers you
No duplicate schedulingUnique partial index on (endpoint, idempotency_key); CRON ticks de-dup on (job_id, idempotency_key) with ON CONFLICT DO NOTHING
One claimer at a timeSELECT FOR UPDATE SKIP LOCKED inside the claiming transaction
At-least-once deliveryThe dispatch happens before that transaction commits, so a worker killed in the window redelivers. Every HTTP call carries x-invokr-idempotency-key so you can de-dup
Crash recovery, freeAn aborted transaction rolls the claim back; the next poll picks it up in ~200ms. No lease to expire, no reaper to tune
ObservableEvery attempt: duration, status, response body, error — queryable, not just logged
We say at-least-once on purpose. Nobody can honestly promise exactly-once delivery to an arbitrary endpoint.

why not x

What Invokr is not

  • Not a workflow engine. No DAGs, no dependencies between jobs, no compensation logic
  • Not a fan-out bus. One job, one target. If you want five consumers, that is what your broker is for
  • Not long-running orchestration. No durable state machine in your code, no replay of your functions
  • Not ordered. Two jobs queued in order can finish out of order — workers run in parallel
If you need a saga, use a saga. Invokr is for "do this thing, then, reliably" — which is most of what we actually build.
the on-ramp

You do not have to run anything

Library mode: Invokr embeds in a Rust service you already operate, on the PgPool you already have.

// your pool, your migrations, your deploy
let client = InvokrLibraryClient::new(
    pool, "sched_", &enc_key, None)?;

client.provision_workspace("orders").await?;

client.create_job("orders", "send-receipt",
    input, 3,
    JobTrigger::Delayed { run_at },
    Some(&key)).await?;

let handle = client.start_worker(
    MySchemas, WorkerConfig::default());
  • No new service. The worker is a task in your process
  • No new infra. Your Postgres, with a table prefix so our tables stay out of your way
  • No new on-call. It pages you the way your service already does
  • Same InvokrClient trait as the HTTP client — when you outgrow embedded, you swap the constructor and your call sites do not change
Service mode is the same code with an HTTP hop in front. Start embedded; graduate when you have a reason.
what we have not built

These are questions, not a roadmap

Deliberately unbuilt. We would rather hear which of these blocks you than guess.

  • Dead-letter handling. A job that exhausts its retries is FAILED and sits there. Should it land somewhere you can drain and re-drive?
  • Idempotency-key propagation. HTTP targets get x-invokr-idempotency-key automatically; for Kafka and Redis Stream you template it in yourself. Should that be automatic?
  • Per-endpoint rate limiting. Nothing today stops a backlog from flooding your downstream. Who hits this first?
  • Schedule backfill. A CRON job that was retired for six hours has a hole. Do you want those ticks replayed, or is the hole correct?
  • Noisy-neighbour isolation. Tenants share a worker pool. At what point does that stop being acceptable for you?
Bring us one thing you would need before you would migrate.
the ask

Two asks

  • Who wants to be the first migration? We will do the integration with you, in library mode, against your existing Postgres — and we will own the first incident
  • Bring your worst tracker incident. We will tell you honestly whether Invokr would have prevented it. Sometimes the answer is no, and we would rather you hear that from us

appendix

Temporal, in more detail

what temporal gives you

  • Durable execution of your code, with replay and deterministic history
  • Long-lived workflows with state that survives process death
  • Sagas, compensation, child workflows, signals

why that is a different axis

  • You write workflow code against an SDK; Invokr takes a row and calls an endpoint
  • Cluster, history service, matching service, visibility store — versus two processes and the Postgres you already run
  • For "call this URL in 15 minutes, retry on failure", the workflow model is a lot of machinery
The honest framing: if your problem is orchestration, Temporal is the better tool. If your problem is deferred delivery, Invokr is a tenth of the surface area.
appendix

Tenancy and retry math

schema-per-workspace

  • public holds only orgs and workspaces
  • Each workspace gets its own schema: endpoints, jobs, executions, attempts, secrets
  • Requests carry X-Org-Id + X-Workspace-Id; the connection's search_path is scoped per request
  • The worker sweeps active schemas from a registry cached for 30s
  • Same endpoint name in two workspaces is two unrelated rows — demo scene 7

backoff

  • fixed — initial_delay_ms
  • linear — initial × attempt
  • exponential — initial × 2^(attempt-1)
  • All three: ±25% jitter, clamped to max_delay_ms
  • The worker writes run_at = now() + backoff and releases the row — it does not sleep holding a claim
appendix

Odds and ends worth having ready

cron versioning

  • Immutable: an update retires v1, creates v2, chained by previous_version_id
  • GET …/versions returns the chain for audit
  • A reaper — itself an Invokr CRON job — retires expired schedules and unschedules pg_cron in the same transaction

secrets

  • AES-256-GCM at rest; optional AWS KMS for the key
  • Write-only: GET returns name and timestamps, never the value
  • Resolved in the worker at dispatch, cached 300s, sent only to the target

sdks

  • Smithy model is the source of truth
  • TypeScript and Rust clients are generated from it
  • A Haskell example is in-tree, against the same API

metrics

  • Prometheus on the API and the worker
  • Jobs created, executions claimed and completed, dispatch latency by transport
  • Grafana dashboard ships in monitoring/
