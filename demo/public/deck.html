the mental model

You already know this API

If you have written JavaScript, you have written half of Invokr.

What you want JavaScript Invokr
Fire now setTimeout(fn, 0) POST /v1/jobs { trigger: IMMEDIATE }
Fire later setTimeout(fn, 5000) POST /v1/jobs { trigger: DELAYED, run_at }
Fire repeatedly setInterval(fn, 60000) POST /v1/jobs { trigger: CRON, cron }
Cancel clearTimeout(id) POST /v1/jobs/{id}/cancel
Except it survives crashes, retries with backoff, de-duplicates on your idempotency key, and every attempt is on the record.

what invokr is

What the create writes

trigger jobs executions
IMMEDIATE one row one row — run_at = now()
DELAYED one row one row — run_at is what you sent
CRON one row none — pg_cron inserts one per tick
Both writes happen in one transaction, before the API answers.
what invokr is

There is no scheduler

The POST writes both rows in one transaction. Everything after that happens inside the database.

Crash recovery

Time What happens The row, in the database
t+0ms worker_b2e7 claims exec_4f2c and starts delivering RUNNING · worker_b2e7
t+340ms worker_b2e7 is SIGKILLed mid-delivery the transaction never commits
t+340ms PostgreSQL rolls the whole claim back with it QUEUED · worker_id NULL
t+520ms the next poll from worker_c9d4 picks it straight up RUNNING · worker_c9d4
There is no monitoring worker watching for stuck jobs. The claim and the delivery are the same transaction, so a worker that dies never committed either one.

the on-ramp

You do not have to run anything

Library mode: Invokr embeds in a Rust service you already operate, on the Postgres you already have. 

let client = InvokrLibraryClient::new(
    pool, "sched_", &enc_key, None)?;

client.provision_workspace("orders").await?;

client.create_job("orders", "send-receipt",
    input, 3,
    JobTrigger::Delayed { run_at },
    Some(&key)).await?;

let handle = client.start_worker(
    MySchemas, WorkerConfig::default());
  • No new service. The worker is a task in your process
  • No new infra. Your Postgres, with a table prefix so our tables stay out of your way
  • Service mode is the same code with an HTTP hop in front. You can start embedded and move to service when you have a reason.

Temporal, in more detail

what temporal gives you

  • Durable execution of your code, with replay and deterministic history
  • Long-lived workflows with state that survives process death
  • Sagas, compensation, child workflows, signals

why that is a different axis

  • You write workflow code against an SDK; Invokr takes a row and calls an endpoint
  • Cluster, history service, matching service, visibility store — versus two processes and the Postgres you already run
  • For "call this URL in 15 minutes, retry on failure", the workflow model is a lot of machinery
The honest framing: if your problem is orchestration, Temporal is the better tool. If your problem is deferred delivery, Invokr is a tenth of the surface area.
appendix

Tenancy and retry math

schema-per-workspace

  • public holds only orgs and workspaces
  • Each workspace gets its own schema: endpoints, jobs, executions, attempts, secrets
  • Requests carry X-Org-Id + X-Workspace-Id; the connection's search_path is scoped per request
  • The worker sweeps active schemas from a registry cached for 30s
  • Same endpoint name in two workspaces is two unrelated rows — the demo's "same name, two teams"

backoff

  • fixed — initial_delay_ms
  • linear — initial × attempt
  • exponential — initial × 2^(attempt-1)
  • All three: ±25% jitter, clamped to max_delay_ms
  • The worker writes run_at = now() + backoff and releases the row — it does not sleep holding a claim
appendix

Odds and ends worth having ready

cron versioning

  • Immutable: an update retires v1, creates v2, chained by previous_version_id
  • GET …/versions returns the chain for audit
  • A reaper — itself an Invokr CRON job — retires expired schedules and unschedules pg_cron in the same transaction

secrets

  • AES-256-GCM at rest; optional AWS KMS for the key
  • Write-only: GET returns name and timestamps, never the value
  • Resolved in the worker at dispatch, cached 300s, sent only to the target

sdks

  • Smithy model is the source of truth
  • TypeScript and Rust clients are generated from it
  • A Haskell example is in-tree, against the same API

metrics

  • Prometheus on the API and the worker
  • Jobs created, executions claimed and completed, dispatch latency by transport
  • Grafana dashboard ships in monitoring/
what invokr is

Architecture

There is no scheduler process. The database is the scheduler.
pg_cron materializes CRON ticks inside PostgreSQL. Delayed jobs are claimed straight off the worker's pickup query when run_at <= now(). Two processes, one database, nothing holding a timer in memory.
