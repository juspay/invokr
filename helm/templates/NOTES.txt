────────────────────────────────────────────────────────────────────────
1. VERIFY pg_cron IS ACTUALLY LIVE
────────────────────────────────────────────────────────────────────────
Invokr does not schedule CRON jobs itself -- it delegates to the pg_cron
Postgres extension. If pg_cron is not loaded, everything below will look
healthy and CRON jobs will simply never fire.

  psql "$INVOKR_DATABASE_URL" -c "SELECT * FROM cron.job;"

An error here means the extension is not loaded. Two things are required, and
BOTH are the database operator's job -- this chart cannot do either:

  a) shared_preload_libraries = pg_cron   (a STATIC parameter: it needs a
     database restart before it takes effect, even though the change applies
     cleanly without one)
  b) cron.database_name = {{ .Values.database.name }}

Also confirm INVOKR_DATABASE_URL points at the WRITER endpoint. pg_cron runs
jobs only on the writer; a reader gives you a working API and zero executions.

────────────────────────────────────────────────────────────────────────
3. BOOTSTRAP AN ORG AND WORKSPACE
────────────────────────────────────────────────────────────────────────
Invokr is multi-tenant and has no tenants until you create one. Nothing works
until this is done -- it is not automated by this chart.


{{- $oidc := eq (.Values.apiConfigs.auth_mode | default "disabled") "oidc" }}
{{- if $oidc }}
These calls need a credential: an OIDC access token, or a scoped API token if
you set `api_token_prefix` and `api_static_tokens` in apiConfigs/secrets.
{{- else }}
auth_mode is `disabled`, so these calls carry no credential -- and neither does
anything else that can reach the API.
{{- end }}

  curl -X POST "$INVOKR_URL{{ include "invokr.pathPrefix" . }}/v1/orgs" \
{{- if $oidc }}
    -H "Authorization: Bearer $TOKEN" \
{{- end }}
    -H 'Content-Type: application/json' \
    -d '{"name": "Your Org", "slug": "your-org"}'

  curl -X POST "$INVOKR_URL{{ include "invokr.pathPrefix" . }}/v1/orgs/<org_id>/workspaces" \
{{- if $oidc }}
    -H "Authorization: Bearer $TOKEN" \
{{- end }}
    -H 'Content-Type: application/json' \
    -d '{"name": "Your Workspace", "slug": "your-workspace"}'

Creating a workspace provisions its schema, so give it a moment to complete.

────────────────────────────────────────────────────────────────────────
!! APPLY SCHEMA MIGRATIONS BEFORE SERVING TRAFFIC
────────────────────────────────────────────────────────────────────────
No schema migrations ran. Against an empty database the API fails on every
request, and the org/workspace steps above will not work.

The api image has no migrate-and-exit path yet, so this is a manual step for
now. Apply the SQL from the repository's migrations/ directory, in filename
order:

  for f in migrations/*.sql; do
    psql "$INVOKR_DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"
  done

Once the image supports it, set migration.enabled=true and the chart runs this
as a pre-install hook instead.
{{- end }}

────────────────────────────────────────────────────────────────────────
!! THIS INSTALL IS UNAUTHENTICATED
────────────────────────────────────────────────────────────────────────
apiConfigs.auth_mode is `disabled`, so every request is served as a development
identity and no credential is required or checked. Anyone who can reach these
pods has full access to every workspace on this install.

api.ingress.enabled is {{ .Values.api.ingress.enabled }}. Keep the API off the public
internet until you set apiConfigs.auth_mode=oidc and point it at an IdP:

  apiConfigs:
    auth_mode: oidc
    oidc_issuer_url: https://your-idp/
    oidc_client_id: invokr
    oidc_redirect_host: https://invokr.your-domain
  secrets:
    oidc_client_secret: <secret>
{{- end }}
